## Constraints

_Things the implementation must respect: existing APIs, performance budgets, browser support, data shapes._

- Keep the change in the zero-build vanilla-JS stack; no new framework or build step.
- Use the current v2 retail envelope shapes. Manifest Goldback metadata currently arrives as `metal: "goldback"` with `weight_oz: 1` for G1 slugs, while hardcoded fallback metadata uses fine-ounce weight (`0.001`) for `goldback-oklahoma-g1`; premium calculation must not depend on Goldback `weightOz`. The shared helper should identify the Goldback benchmark from metal/slug/rate context, not from `weightOz` — the market-sorting fixture deliberately sets Goldback weight to `0` while still expecting `+20.0%` from the G1-rate path.
- Do not treat `isGoldbackRetailLookup` as an available predicate. It has no live code matches; market Goldback detection should come from metadata/slug/rate context already in `market-data.js` and `retail.js`.
- Avoid duplicating premium math. The three in-scope render sites are in `js/market-data.js`, so a local helper can cover this — but it must encapsulate **benchmark selection** (spot vs G1 rate) alongside calculation and tier classification, not just the arithmetic. The three surfaces diverge today: ticker and detail modal are spot-only (broken for Goldback), Matrix has the G1 fallback. A helper that only consolidates `((price - benchmark) / benchmark) * 100` without standardizing "which benchmark for which metal" doesn't solve the actual duplication. DOM rendering stays per-surface (ticker uses `<span class="premium">`, Matrix and detail modal use `<span class="vp-premium low|high">`). Testing through DOM-level Playwright assertions (class names + text content) is sufficient without exposing the helper to `window`.
- Preserve vendor availability rules: ticker and Matrix skip disabled market-filter cells via `_isMarketItemEnabled()`, and ticker picks only in-stock vendors.
- Keep display currency behavior intact. Retail prices format through `formatCurrency()` and existing currencychange/refresh paths; premium percentages remain percentages and should not be currency-converted. (Verified: since both price and benchmark are in the same currency, currency conversion doesn't affect the percentage.)
- Do not reuse inventory Goldback valuation semantics. `js/goldback.js` and `viewModal.js` handle denomination/inventory pricing and purchase premium; STRK-85 is about current dealer markup in market surfaces.
- Current service-worker TTL behavior already classifies `/v2/goldback/latest.json` as an enveloped 25 h family; avoid adding a second ad hoc freshness policy in the UI.
- CSS must update both ticker premium text and `.vp-premium` badges. Existing `.vp-premium.low` currently means "under 10%" and maps to warning/yellow, so class-name migration needs deliberate handling in approach.

## Open Questions

_Things that need answering before approach.md can be written. If non-empty, stop here and resolve with the user._

- None blocking. Discovery verified that Goldback rows are present in the current retail data path and that `/goldback/latest.json` exposes the expected G1 rate.
- Approach should still decide whether to preserve `low` / `mid` / `high` class names with new semantics or introduce less overloaded class names.
- Approach should decide the **ticker visual rendering**: should Goldback ticker premium adopt `vp-premium`-style tier colors, or stay muted text with just the percentage? This is a design decision that affects CSS scope.
- Approach should decide whether `_goldbackG1Rate` failure keeps Goldback premium blank, as live code does today, or retries the same v2 source on `refreshMarketData()` / `currencychange`. Currently `initMarketData()` is the only G1-rate fetcher (lines 1400-1416); `refreshMarketData()` and `currencychange` only re-render (lines 1424-1439), so a failed initial fetch persists as blank premium until page reload. Requirements make cross-module fallback (e.g. reusing `goldback.js`'s separate `goldbackPrices`) out of scope unless the approach intentionally changes that boundary — but retrying the same endpoint on refresh is a lighter decision.
- Testing note: the market-sorting fixture's `weight: 0` for Goldback is intentional scaffolding (live manifest returns `weight_oz: 1`). New tests should explicitly assert the invariant "weight doesn't matter for Goldback premium" rather than relying on a fixture that happens to use `0`.

## Discovery Summary

_2–3 sentences: where the work will land, what looks tricky, what's already easy._

STRK-85 should land primarily in `js/market-data.js` and `css/styles.css`, with Playwright coverage extending existing market fixtures. **Two surfaces are fully broken** — ticker (line 293) and detail modal (line 772) have no `_goldbackG1Rate` fallback at all — while only the Matrix (line 1142) has a working Goldback premium path today. The approach needs to add benchmark-selection logic to ticker and detail modal, consolidate tier classification across all three surfaces, and decide class-name semantics and explicit failure behavior when `_goldbackG1Rate` is unavailable.

**Top Concerns**

1. **Detail modal Goldback premium gap is understated.** The discovery's Existing Code row for lines 713-784 says it "currently uses spot-only premium math plus the binary `premium < 10 ? "low" : "high"` badge" — but this doesn't clearly flag that the detail modal has **no `_goldbackG1Rate` fallback**, unlike the Matrix (which does, at line 1142). The approach phase needs to treat the detail modal as a third broken surface alongside the ticker, not lump it with the Matrix. The premium code diverges structurally:
   - **Ticker** (line 292-298): `_getSpotPrice(metalLower)` → null for Goldback → premium null → no text rendered.
   - **Detail modal** (line 772): `_getSpotPrice(metalCode)` → null for Goldback → premium skipped → "—" rendered.
   - **Matrix** (line 1138-1145): `_getSpotPrice(isoCode)` → null, but falls through to `_goldbackG1Rate` → premium computed.
     All three are in `js/market-data.js`, but the fix patterns are different: ticker needs a Goldback branch added where none exists; detail modal needs its `else` branch extended; Matrix only needs tier classification updated.

2. **`weightOz` red herring in the detail modal.** The constraint at line 61 says "premium calculation must not depend on Goldback `weightOz`" and the discovery validates this for the Matrix path (where `_goldbackG1Rate` bypasses the weight check entirely). But in the **detail modal** at line 772, the condition is `spotPrice > 0 && weightOz > 0`. For Goldback slugs with manifest `weight_oz: 1`, `weightOz` would be `1` (truthy). The spot-price null gate fires first, making `weightOz` irrelevant today — but a naïve fix that only adds a G1 fallback to the detail modal might accidentally create a `meltValue = spotPrice * 1` path that computes wrong premium if `spotPrices["goldback"]` ever becomes populated. The approach should ensure the G1-rate path is reached via metal/slug detection, not by waiting for the spot path to fail.

3. **Fixture `DEFAULT_GOLDBACK.g1_usd` equals `DEFAULT_RETAIL_LATEST["utah-1-goldback"]` vendor price.** Both are `4.25` (`fixtures.js:84` and `fixtures.js:113`). This means the fixture's Goldback premium is `0%` — which won't exercise tier classification. The market-sorting test works because it uses its own fixture with `goldbackG1 = 4.25` and vendor price `5.10` (yielding `+20.0%`). The approach should note that new ticker/detail-modal tests need a non-zero premium spread — either by adjusting `DEFAULT_GOLDBACK` or using custom overrides like the market-sorting fixture does.

> OPUS: The discovery's constraint "avoid duplicating premium math" (line 64) is well-founded but deserves a nuance: the three surfaces don't just duplicate the _calculation_, they duplicate the _benchmark selection logic_ (spot vs G1). A shared helper should encapsulate both "pick the right benchmark for this metal" and "compute premium + tier", not just the arithmetic. The Matrix already has this logic inline; the other two surfaces are missing it entirely.

> OPUS: The CODEX inline comment on constraint line 65 about testing local helpers via `page.evaluate()` is correct — but there's a simpler path the approach should consider: since all three surfaces produce DOM elements with class names (`.premium`, `.vp-premium.low`, `.vp-premium.high`), the tier classification can be fully tested through DOM assertions without exposing the helper. Only the premium _value_ accuracy needs a numeric check, and that's already covered by `toContainText("+20.0%")` patterns.

**Unverified Assumptions**

- **The discovery assumes the three premium render paths are structurally similar enough for "a local helper."** In practice, the ticker builds premium as a text-only `<span class="premium">`, the Matrix builds it as a `<span class="vp-premium low|high">` badge appended to a price cell, and the detail modal builds it as a `<span class="vp-premium low|high">` badge in its own `<td>`. A shared helper for _calculation + tier classification_ is clean, but the DOM rendering must remain per-surface. The approach should be explicit about what the helper returns (e.g., `{ value: number, tier: string, text: string }`) vs what each render site does with it.
- **The discovery assumes `_goldbackG1Rate` is sufficient as the sole Goldback benchmark.** Currently only `initMarketData` populates it, and there's no retry. If the user navigates to a Goldback detail modal after a failed G1 fetch, the detail modal will show "—" for every vendor's premium. The approach should decide whether this is acceptable or whether `goldback.js`'s separate `goldbackPrices` (which also fetches `/goldback/latest.json` at `js/goldback.js:420+`) could serve as a fallback source — at the cost of coupling two independent modules.
- **The discovery doesn't address how the ticker's Goldback premium text should render visually.** The ticker currently uses the generic `.premium` class (no tier), while the Matrix/detail-modal use `.vp-premium.low|high`. Should the ticker adopt `vp-premium`-style tier colors, or should it stay muted text with just the percentage? This is a design decision the approach phase needs to resolve, and it affects CSS scope.
- **The market-sorting fixture's `weight: 0` for Goldback (line 52) is intentional test scaffolding, not a reflection of production data.** The live manifest returns `weight_oz: 1` for G1 Goldback slugs (confirmed via API probe). A test that validates the "weight doesn't matter for Goldback premium" invariant should explicitly assert this, not rely on a fixture that happens to use `0`.

2. **Ticker premium gap is structural, not incidental**. The discovery correctly identifies that `_getSpotPrice("goldback")` returns `null`, but doesn't explicitly note that the ticker's premium calculation (lines 292-298) has **no Goldback fallback path at all** — unlike the vendor table (lines 1138-1145) which has the `_goldbackG1Rate` fallback. 3. **`_goldbackG1Rate` fetch timing race**. The discovery notes that fetch failure "only logs a warning and leaves `_goldbackG1Rate` null" (line 1413-1415). What's not called out: `initMarketData` calls `renderBestPriceTicker()` and `renderVendorPrices()` **after** the Goldback fetch attempt (lines 1418-1419), but the fetch is async and non-blocking. If the fetch fails, Goldback premium is blank on initial render with no retry path. The `refreshMarketData` function (line 1424-1427) also doesn't re-fetch the Goldback rate. This is a latent failure mode the approach should address. _(CODEX correction: the fetch is awaited, so the initial render happens after success or failure — the confirmed risk is the no-retry path after failure, not a timing race.)_
