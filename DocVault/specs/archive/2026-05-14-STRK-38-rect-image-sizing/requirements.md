# STRK-38 — Requirements

> **Source Issue:** [STRK-38](https://plane.lbruton.cc/lbruton/browse/STRK-38/)
> **Title:** Card/table view: rectangular item images don't auto-size like item detail modal
>
> **Issue body summary:**
> In card views (A/B/C) and table views, rectangular items (bars, notes, Silverbacks, proof sets)
> render their images floating inside a lighter blue rectangle container with dead space around them.
> Round coins are properly masked behind circular placeholders, but rectangular items don't get
> equivalent shape-aware treatment.
>
> The **item detail modal** already handles rectangular items correctly — it auto-sizes/trims the
> width to fit the bar or note image without the awkward container.
>
> Fix direction: research how the item detail modal handles non-circular image layouts and apply the
> same pattern to card and table views. Options:
>
> - Trim to fit the image aspect ratio (like the detail modal), or
> - Use `object-fit: contain` with a transparent/matching background instead of the contrasting blue rectangle
>
> Per-item image layout configuration (horizontal vs vertical stacking) is a separate future issue.

## Overview

Rectangular items (bars, notes, Silverbacks, Goldbacks, proof sets) display poorly in card views (A/B/C) and the table view. The `.coin-img` container uses fixed square dimensions with a visible `--bg-tertiary` background, causing rectangular images to float with dead space. The item detail modal already solves this via the `.view-shape-rect` pattern — `width: auto; height: auto` with `max-width`/`max-height` bounds and no contrasting background. This sketch brings the same shape-aware sizing to card and table views so rectangular items render as cleanly as coins do.

## User Stories

- **US-1:** As a collector with bars and notes in my inventory, I want rectangular items in card views to render with their natural aspect ratio (no dead-space box), so that the portfolio view looks polished and professional.
- **US-2:** As a user browsing in table view, I want rectangular item thumbnails to not have a contrasting background rectangle around them, so that they blend cleanly with the row like round coin thumbnails do.
- **US-3:** As a user switching between card styles (A/B/C) and the detail modal, I want rectangular items to look visually consistent across all views, so that the experience feels cohesive.

## Acceptance Criteria

### AC-1 — Card A: rectangular images fill naturally (maps to US-1, US-3)

- **Given** a rectangular item (bar, note, Silverback, or Goldback) with an image
- **When** rendered in Card Style A (sparkline header)
- **Then** the image renders with `object-fit: contain` within the container, and the container has no visible contrasting background box (no `--bg-tertiary` dead space around the image)

### AC-2 — Card B: rectangular images fill naturally (maps to US-1, US-3)

- **Given** a rectangular item with an image
- **When** rendered in Card Style B (full-bleed overlay)
- **Then** the image container adapts to the rectangular aspect ratio within the card's size constraints, with no visible contrasting background rectangle

### AC-3 — Card C: rectangular images fill naturally (maps to US-1, US-3)

- **Given** a rectangular item with an image
- **When** rendered in Card Style C (split card, image left)
- **Then** the image fills its column proportionally without a visible contrasting background box, maintaining the rectangular aspect ratio within the column's width constraint

### AC-4 — Table view: rectangular thumbnails blend with row (maps to US-2)

- **Given** a rectangular item with an image
- **When** rendered in table view (Style D)
- **Then** the thumbnail has no visible contrasting background rectangle; the image blends with the row background like round coin thumbnails do

### AC-5 — No-image placeholders still work (regression guard)

- **Given** a rectangular item with no image available
- **When** rendered in any card or table view
- **Then:**
  - **Card views:** a metal-tinted placeholder renders with a rectangular shape (matching the existing `.cv-no-image` glass-orb effect but with rectangular `border-radius` via `.bar-shape`), not a broken or invisible layout
  - **Table view:** the SVG placeholder generated by `_getThumbPlaceholder()` uses a rectangular outer shape for rect items (currently all placeholders use a circular `<circle>` outer background regardless of item type — this must be updated)

### AC-6 — Round items are unaffected (regression guard)

- **Given** a round item (any standard coin) with or without an image
- **When** rendered in any card or table view
- **Then** the item renders identically to its current behavior — circular mask, centered, no layout shift

### AC-7 — Image frame overrides respected (regression guard)

- **Given** an item with a manual image frame override (`obverseImageFrame` or `reverseImageFrame` set to `"circle"` or `"rectangle"` via the add/edit modal toggle)
- **When** rendered in any card or table view
- **Then** the override takes precedence over the auto-detected shape, consistent with how the detail modal already honors `resolveImageFrame()`. Acceptance evidence must cover Card B and Card C in addition to the existing table + Card A + modal test coverage.

## Non-Goals

- Not implementing per-item image layout configuration (horizontal vs vertical stacking in the image block) — separate future issue per STRK-38
- Not redesigning the card layout structure — only adjusting how the `.coin-img` container sizes for rectangular items within the existing card HTML
- Not changing the detail modal's image rendering — it is the reference implementation, not the target
- Not adding new image-frame auto-detection heuristics — `resolveImageFrame()` in `image-frame.js` already handles shape resolution; this sketch only consumes its output more effectively in card/table CSS
- Not implementing portrait-vs-landscape intrinsic aspect-ratio sizing — `resolveImageFrame()` returns only `"round"` / `"rect"` with no orientation data, and mixed per-side orientations (e.g. portrait obverse + landscape reverse) need UI prototyping before a design can be committed. File as a follow-up issue.
- Not changing how images are loaded, cached, or resolved — only how they are displayed after loading

## Open Questions

1. **Table placeholder SVGs** — `_getThumbPlaceholder()` generates all placeholders with a circular `<circle>` outer shape. Should rect items get a `<rect>` outer shape, or is transparent background + contain sufficient for the placeholder path too?
2. **Card B/C wrapper constraints** — Card B and Card C have separate CSS wrapper dimensions from Card A. Discovery should confirm whether their `.coin-img` / `.bar-shape` sizing needs distinct treatment or whether a shared rule works across all three.
3. **JS contract changes** — Card/table shape state is assigned in JS (class toggling, inline `object-fit`). Discovery should confirm whether changes are CSS-only or require JS modifications to the rendering helpers.

### Codex

**Verified:**

- StakTrakr is still a vanilla-JS PWA with strict script-order/global-contract constraints per DocVault Foundation docs (`Projects/StakTrakr/Overview.md`, `Projects/StakTrakr/Foundation/architecture.md`, `Projects/StakTrakr/Foundation/coding-standards.md`).
- The detail modal applies rectangular rendering by toggling `.view-shape-rect` from `resolveImageFrame()` and sizing rect images with `width:auto`, `height:auto`, `max-width`, and `max-height` (`js/viewModal.js:2185-2189`, `css/styles.css:6093-6105`).
- Card views already consume `resolveImageFrame()` in `_cardImageHTML()` and use `.bar-shape` plus `object-fit:contain`; Card A/B/C then impose separate fixed wrapper dimensions (`js/card-view.js:549-575`, `css/styles.css:13494-13505`, `css/styles.css:13609-13615`, `css/styles.css:13680-13684`, `css/styles.css:13729-13737`).
- Table view already consumes `resolveImageFrame()` via `.table-thumb-rect`, but thumbnail sizing remains 28px square and no-image fallbacks are generated SVG data URIs (`js/inventory-table.js:513-541`, `css/styles.css:5290-5309`, `js/inventory-table.js:245-273`).
- Existing override tests cover table, Card A, and the detail modal, but not Card B or Card C (`tests/playwright/image-frame-override.spec.js:123-159`).

**Top concerns:**

1. AC-1 asks for landscape vs portrait natural aspect behavior, but the live frame resolver exposes only `round` vs `rect`; requirements need to specify whether intrinsic image dimensions are in scope.
2. AC-5 describes `.cv-no-image` placeholders across card and table views, but table view does not use `.cv-no-image`; its no-image path is a lazy-loaded SVG thumbnail and currently includes a circular outer SVG background.
3. AC-7 says frame overrides work in any card/table view, while existing test coverage only proves table, Card A, and modal; Card B/C need explicit acceptance evidence or the AC should be narrowed.

**Unverified assumptions:**

- The STRK-38 source issue intends portrait-vs-landscape wrapper sizing, not only transparent backgrounds and `object-fit:contain`.
- The table no-image state should visibly render a rectangular placeholder rather than simply hide a missing thumbnail or show a generic SVG fallback.
- Changing card/table thumbnail wrappers is acceptable within "not redesigning the card layout structure."
- The future per-item horizontal/vertical stacking issue does not own portrait-vs-landscape image orientation.
- Visual acceptance can be verified from DOM/CSS assertions without screenshot-level checks for the dead-space background.
