STRK-67 Frame Toggle — UI Mockups

Four corner-toggle variants for the per-side obverseImageFrame / reverseImageFrame override (AC-7). Click the toggle on each slot to cycle through auto → circle → rectangle; the slab image's clipping changes so you can compare the end-to-end visual effect, not just the affordance.

A Cycle button — current-state glyph

Single corner button. Face shows current value. Click cycles auto → circle → rectangle.

state:auto
resolves:rectangle
click:cycle
  • + Smallest footprint, no extra DOM beyond a button
  • + One affordance, one interaction model
  • − Glyph swap can blur the "I'm in auto mode" state
  • − Cycle order is hidden; needs hover title

Trade-off recap

Property A — Glyph cycle B — Icon + badge C — Popover D — Chip strip
Footprint in modal smallest small small (collapsed) +28px vertical
Discoverability low (cycle hidden) medium high high
Current-state legibility medium (glyph swap) high (badge) high (popover label) highest
Clicks to set value 1–3 (cycle) 1–3 (cycle) 2 (open + pick) 1 (direct)
Implementation cost lowest low popover mgmt + outside-click low
Hides correctly when slot is empty (AC-8) trivial trivial trivial requires explicit conditional render

Open questions for the picker

  • Should the toggle hint at which direction the auto resolves to? E.g., when in auto and the resolved value is "rectangle," do we tint the badge or annotate the tooltip?
  • Long-press / right-click reset to auto? Or is cycle-back-to-auto sufficient?
  • Keyboard: tab focus, then space/enter to cycle (A, B) or open popover (C) or focus-then-arrow within strip (D)? D is most accessible by default.
  • Color treatment when auto vs explicit override: subtle? loud? StakTrakr's gold accent suggests we reserve it for "user has overridden" so the unmodified default doesn't shout.
